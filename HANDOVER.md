## 2. Key architectural decisions (the "why," not just the "what")

### Crypto: real libsodium on both ends, never a reimplementation
- **Backend**: PyNaCl, calling libsodium's low-level bindings directly (`nacl.bindings`), not the higher-level `SecretBox` (which is XSalsa20-Poly1305, a *different* construction).
- **Mobile**: the `sodium` Dart package (**not** `sodium_libs` — that's discontinued, replaced by `sodium` directly as of its v4.0 native-assets rewrite).
- **Why both sides bind to the actual C library**: a pure-Dart or pure-Python reimplementation of XChaCha20-Poly1305/Ed25519 would be a *second, independent implementation* of the same crypto that could silently drift from the other side. Binding both to libsodium eliminates that risk entirely.
- **Wire format is a 27-byte fixed-width binary struct**, not JSON (`backend/app/mesh/wire_format.py` / `mobile/lib/core/crypto/wire_format.dart`). Ed25519 signs raw bytes; JSON would require both languages to agree on canonical serialization (key order, float formatting), a classic cross-language "signature verification fails intermittently" bug. Big-endian, fixed-point lat/lng (×1e7) instead of floats, for the same unambiguity reason.
- **This wire format is proven byte-for-byte compatible with permanent regression tests in both repos** (not just each side's own unit tests): `backend/tests/test_wire_format_interop.py` decodes a fixture generated by the real Dart client; `mobile/test/core/crypto/wire_format_interop_test.dart` decodes one generated by the real Python backend. If you ever change the wire format, regenerate both fixtures (Dart side: `dart run tool/generate_interop_fixture.dart` from `mobile/`).

### Storage: atomic JSON blobs, not scattered keys
`SecureStorageManager` (`mobile/lib/core/storage/`) stores `StoredDeviceIdentity`, `StoredAccount`, and `StoredSession` each as **one JSON blob under one key**, not as several separate key-value pairs. Writing related fields separately risks the app being killed mid-write and leaving e.g. a session token persisted without its sector key. One write, one atomic unit.

The actual storage backend is injected behind a `KeyValueStore` interface — production uses `flutter_secure_storage` (Keychain/Keystore), tests use an in-memory fake. This is what makes storage logic testable without a real platform channel (which doesn't exist in a bare `flutter test` host process).

### State management: Riverpod `StateNotifier` + sealed-class states
`AuthController` and `JoinController` are `StateNotifier`s exposing sealed classes (`AuthState`, `JoinState`) so the UI can exhaustively `switch` over every phase with no missed-case risk. `ApiClient` is deliberately **stateless with respect to auth** — every method takes its bearer token as an explicit parameter rather than the client holding "the current token" as mutable state; the controllers own token lifecycle.

Device registration is retry-safe by construction: the Ed25519 keypair is generated and persisted to Secure Storage *before* any network call, so a dropped connection between "generate key" and "confirm registration" never causes a second keypair on retry. A 409 "already registered to you" conflict from the backend is treated as success (recovered via `GET /devices`), not failure.

### Backend geospatial/coverage decisions (Phases 0–4, still governing)
- **PostGIS `ST_Buffer` on `geography`** for swath buffering, not shapely+pyproj UTM reprojection in Python — `geography` buffering computes true ground-distance meters natively.
- **H3 hexagonal grid, resolution 12** (~9.4m edge) for the coverage ledger.
- **Search-theory POD formula lives in exactly one place**: the SQL function `recalc_hex_coverage()` (migration 0001). Never reimplemented in Python — tests drive the real function, they don't duplicate its math.
- **CQRS-style ledger**: `hex_contributions` (immutable, one row per traverse-episode) + `hex_coverage_state` (derived, rebuildable from the ledger at any time).
- **Realtime broadcast is a property of the data changing**, not application code remembering to notify: `AFTER INSERT OR UPDATE` triggers on `hex_coverage_state`/`device_presence` fire `pg_notify`. Verified empirically (not assumed) that Postgres collapses identical `(channel, payload)` notifications fired within one transaction into a single delivery — so a bulk UPSERT touching hundreds of rows produces exactly one notification.
- **WebSocket auth uses short-lived, single-use tickets** (`POST .../ws-ticket` → `WS ?ticket=...`), not a bearer token in the URL query string (which would land in every proxy/access log).

### Location tracking: battery-aware sampling tiers, packet construction decoupled from upload
- **`LocationSamplingPolicy` (`mobile/lib/core/location/location_sampling_policy.dart`) is pure logic**, no plugin import, mapping `(batteryPct, isCharging) -> SamplingTier` (distance filter in meters + an accuracy hint). Tiers: high (≥60%, 10m), balanced (30–59%, 25m), saver (15–29%, 50m), critical (<15%, 100m) — charging always forces `high` regardless of level. Distance-filtered sampling, not fixed-interval polling, per the original architecture review's Q8: a stationary searcher shouldn't drain the battery for zero new track data.
- **`LocationTrackingController` re-checks the tier after every emitted sample** (not on a separate timer) and re-subscribes to `LocationSource` at the new tier when it changes — keeps the whole controller driven by the position stream, with no wall-clock dependency, which is also what makes it testable via a fake stream with no `fake_async`.
- **`stop()` is synchronous and does NOT await `StreamSubscription.cancel()`** — deliberately. Under `testWidgets`'s test zone, a broadcast `StreamController`'s `cancel()` future was observed to never resolve while `tester.pump()` calls kept being issued back-to-back (see the "known gotchas" entry below); not depending on it also means state reflects "stopped" immediately and a slow/stalled cancel can never block the UI.
- **Telemetry packet construction mirrors the backend exactly**: `TelemetryPacketBuilder` (`mobile/lib/core/location/telemetry_packet_builder.dart`) does `pack(point) -> sign(payload) -> encrypt(payload || signature)`, producing the same 91-byte plaintext shape as `backend/app/ingest/pipeline.py`'s `_EXPECTED_PLAINTEXT_BYTES`. This is Phase 5c's contribution to the wire contract; Phase 5a's `wire_format.dart`/`mesh_crypto.dart` did the packing/crypto primitives, this phase composes them into an actual packet.
- **The local buffer (`TelemetryBufferStore`) is real SQLite** via `sqflite_common`'s `DatabaseFactory` abstraction — the `sqflite` plugin's factory on Android/iOS, `sqflite_common_ffi`'s factory everywhere else (desktop, tests) — not a fake or an in-memory Dart structure. FIFO-capacity-bounded at 10,000 packets per the original PRD; `peekOldest`/`acknowledge` (not a destructive dequeue) so Phase 5d's upload path can retry safely on a dropped connection.
- **`StoredDeviceIdentity` now also carries `wireId`** (previously only `deviceId`, the UUID) — added because the wire format needs the compact `devices.wire_id`, not the UUID, and it wasn't threaded through to storage before this phase. `AuthController._ensureDeviceRegistered` now saves both together via `withRegistration(...)` (was `withDeviceId(...)`).

### Ingest sync: whole-batch acknowledgement, self-scheduling with backoff
- **`IngestSyncController` (`mobile/lib/core/sync/ingest_sync_controller.dart`) acknowledges (deletes from the buffer) the WHOLE batch it sent on ANY 200 response** from `/ingest`, not just the `accepted` count. This is deliberate, not a bug: `IngestResult`'s docstring explains why -- every count bucket the backend returns (`accepted`, `duplicate`, `decrypt_failed`, `signature_invalid`, `wrong_device`, `malformed`) is a TERMINAL, deterministic outcome for that exact packet; there is no "try again later" category in a 200 response, so retrying a permanently-bad packet would just fail identically forever. A batch is only left buffered for retry when the REQUEST ITSELF didn't get a 200 at all (network failure, timeout, 5xx).
- **Self-scheduling via `Timer`, same pattern as `LocationTrackingController`**: `start()` kicks off a loop that reschedules itself after every attempt -- a short fixed interval when healthy/idle, exponential backoff (`SyncBackoffPolicy`, pure/testable, doubling from 5s up to a 5-minute cap) after a failure. `syncOnce()` is public specifically so tests can drive one attempt directly without waiting on real timers.
- **`stop()` is synchronous**, same reasoning as `LocationTrackingController.stop()`: cancel the `Timer` and flip `_running = false` without awaiting anything, so the UI reflects "stopped" immediately and nothing in-flight can block it.
- **The two controllers are wired together at the UI layer, not internally**: `LocationStatusView`'s Start button calls `LocationTrackingController.start()` then `IngestSyncController.start()` -- but ONLY if tracking actually reached `TrackingActive` (checked explicitly). A real bug caught during this phase: an earlier version started sync unconditionally, so a denied location permission left the sync loop running with nothing useful to do (and, in a widget test, a `Timer` that outlived the test). Stop is unconditional both ways (stopping sync even if tracking already failed is harmless).

### SOS state machine: explicit and immediate, separate from passive presence
- **States**: `active -> acknowledged -> resolved`, or `active`/`acknowledged -> cancelled` (only by the triggering user -- a false alarm). See `backend/migrations/0006_sos.sql` for the full diagram. This is deliberately independent of Phase 4's correlated-silence presence heuristic -- that's a passive INFERENCE from a device going quiet; SOS is an explicit, affirmative "I need help now" action from the searcher. They are not merged into one state machine.
- **At most one OPEN alert per device, enforced by the database, not just application code**: a partial unique index (`sos_alerts_one_open_per_device`, on `device_id` `WHERE status IN ('active','acknowledged')`) makes a second trigger from the same device impossible to land as a duplicate row even under a race between two near-simultaneous requests. `sos_repo.trigger()` is idempotent on top of that (checks first, and also catches the unique-violation race and returns the existing row) -- a shaky-hands double-tap or an app restart mid-emergency must never fork into two concurrent incidents for what is the same emergency.
- **Trigger/cancel use the device's SECTOR SESSION token** (same auth as `/ingest`); **list/acknowledge/resolve use the ACCOUNT token plus the existing Lead/Commander RBAC check** (`require_lead_or_commander`, same as membership moderation) -- those actions happen on a different device (the Sector Lead's), not the volunteer's.
- **A missing trigger location falls back to the device's last known presence point** (`device_presence`, Phase 4) rather than requiring a fresh GPS fix before SOS can even be sent -- hitting SOS is exactly the moment a fresh fix might not have landed yet (canyon, indoors, dead zone).
- **Realtime broadcast follows the established `hex_coverage_state`/`device_presence` pattern exactly**: an `AFTER INSERT OR UPDATE` trigger on `sos_alerts` notifies `sector_sos_channel`; `RealtimeListener` re-queries "what changed since my checkpoint" and broadcasts a `sos_delta` message over the same per-event WebSocket. Verified end-to-end against a real connected client in `backend/tests/test_sos_routes.py::TestRealtimeBroadcast`, mirroring `test_ws_dashboard.py`'s existing proof for hex/presence.
- **Mobile: two independent controllers, not one.** `SosController` (searcher's own trigger/cancel) does not persist across app restarts -- there is no "get my current alert" endpoint, and none is needed, since `trigger()` is idempotent server-side, so pressing the button again after a restart safely lands back on the same open alert. `SosAlertsController` (Lead/Commander's list/acknowledge/resolve) is UI-driven polling (`Timer.periodic`, same convention as `PendingApprovalView`), not a `sos_delta` WebSocket client -- no WebSocket client exists in the Flutter app yet (see gotcha #13).
- **Known scope boundary, not a bug**: `SosAlertsController` reads the acting user's `sectorId` from their OWN `StoredSession`, so a pure Commander who has never joined any sector as a member (the backend allows this; Commanders act via `event.commander_id`, no membership required) has no client-side way to discover a sector's id today. The E2E test (`mobile/test/e2e/sos_e2e_test.dart`) works around this by having the "Commander" character also self-join their own sector purely to populate `sectorId` locally -- the actual authorization still comes from the backend's Commander check, independent of that membership. Fine for this session's scope; would need a "my events/sectors" listing endpoint + screen to close properly.

### Reports: an encrypted/signed ingest-style pipeline, NOT plain CRUD
- **Critical discovery this session, worth re-reading before touching this code**: the `reports` table already existed from **Phase 0** (`migrations/0001_init.sql`) with a schema that deliberately mirrors `track_points` -- Ed25519 `signature UNIQUE` for replay defence, `delivery_path`/`hop_count` for a future mesh relay path, a `recorded_at`/`received_at` split for an untrusted device clock. A first attempt at this phase assumed plain authenticated JSON CRUD (matching SOS's shape) and wrote a migration that tried to `CREATE TABLE reports` again -- it failed loudly (`relation already exists`) before any real damage, but **always check for an existing table before assuming a fresh one is needed**, especially for anything named in Phase 0's schema. The corrected migration (`0007_reports.sql`) only ADDS what Phase 0 didn't have (`updated_at` for the realtime checkpoint query, the NOTIFY trigger) -- it does not recreate the table.
- **Reports use the SAME encrypted envelope construction as location telemetry** (XChaCha20-Poly1305 with the sector key, Ed25519-signed payload), just a different, variable-length wire format: `backend/app/mesh/report_format.py` / `mobile/lib/core/crypto/report_wire_format.dart` is a 24-byte fixed header (which includes a `note_len` field) followed by that many UTF-8 note bytes, then the 64-byte signature -- `peek_note_length`/`peekNoteLength` reads just that one header field so the ingest pipeline can locate the payload/signature boundary before fully unpacking anything. Submission goes through `backend/app/reports/pipeline.py` (`POST /reports`), which mirrors `app/ingest/pipeline.py`'s decrypt→verify→dedup→store shape but is much simpler (no segmentation/coverage/presence side effects).
- **`delivery_path` is hardcoded to `'direct'`** everywhere right now -- mesh relay (Phase 7) and SMS fallback (Phase 6c) don't exist yet, but nothing in the wire format is direct-path-specific, so neither should require a format change when they land.
- **Visibility is broader than SOS's**: `GET /sectors/{id}/reports` uses the ACCOUNT token plus `_require_sector_visibility` (reused from `routes/sectors.py`, same helper `presence.py` already uses) -- any sector member OR staff can see reports, not just Lead/Commander, because a "subject found" or "hazard" report is exactly the kind of information every searcher benefits from, unlike SOS's leadership-only acknowledge/resolve actions. Only `POST /reports/{id}/acknowledge` is Lead/Commander-gated, as a lightweight triage signal (no `resolved`/`cancelled` states -- reports don't need SOS's full state machine).
- **Photo attachments (`photo_object_key` column) are explicitly out of scope** -- no object storage exists anywhere in this codebase; the column stays present (Phase 0's schema) but unpopulated until a later phase.
- **Mobile grabs a fresh GPS fix at submission time** via a new `LocationSource.getCurrentPosition()` one-shot method (added alongside the existing `watch()` stream) -- a report's location is "where you are when you file it," no manual entry, no reuse of stale tracking data.

### Commander Dashboard (6c): plain JS SPA, same-origin, no build step
- **User picked Option A explicitly** (asked via a direct architecture question, not assumed): a web dashboard, not a Flutter screen. Confirms the CORS comment's original intent in `main.py`.
- **No bundler, no framework, no npm project.** `backend/dashboard/` is hand-written ES modules (`app.js` router, `api.js`, `ws.js`, `map.js`, `auth-view.js`, `events-view.js`, `dashboard-view.js`) loaded via `<script type="module">`, served same-origin by FastAPI's `StaticFiles` mount at `/dashboard` (added in `main.py`, right after the routers). Leaflet and h3-js are loaded from CDN (`unpkg.com`) in `index.html` as globals (`L`, `h3`) -- **this means the dashboard needs internet access to load its map/hex libraries**, a real dependency worth knowing about, not an oversight. No SRI hashes on those CDN `<script>` tags (an earlier draft added guessed ones; guessed SRI hashes don't match and silently block the whole page load -- removed rather than risk that).
- **Auth is the same phone/OTP flow as the mobile app** (`POST /auth/otp/request` -> `/auth/otp/verify`), reusing the same `AuthTokenResponse` account token, stored in `localStorage` under `lifesearch_dashboard_token`. No separate dashboard-specific auth exists or was needed -- a Commander is just a `User` who happens to be `events.commander_id`.
- **Event/sector CREATION got added to the dashboard, not just visualization** -- a deliberate scope decision beyond the literal "consume the WS feed" ask. Before this, **no client anywhere** (mobile or otherwise) could create an event or a sector; it only ever happened via direct API calls in tests. Without this, the dashboard would have nothing of its own to show. Sector boundaries are drawn by hand: click points on the map (`TacticalMap.startDrawing`/`finishDrawing` in `map.js`), a plain click-collected polygon, not a proper Leaflet.Draw integration (that's a real dependency that wasn't worth adding for this).
- **The WS ticket is refetched on every connection attempt, including reconnects** (`ws.js`'s `DashboardSocket._connect`) -- tickets are single-use and expire in 30s server-side (`realtime/tickets.py`), so reusing one across a reconnect would never work. Reconnect uses exponential backoff (1s doubling to a 30s cap), same shape as the mobile app's `SyncBackoffPolicy` but a fresh from-scratch JS implementation, not shared code (different language, no shared package between the two clients).
- **The dashboard connects ONE socket per event, not per sector** -- `POST /events/{id}/ws-ticket` + `WS /ws/events/{id}` was already event-scoped server-side (see `ws.py`), so the dashboard shows **every sector of the event at once** on one map (each sector gets a stable color from a fixed palette, `TacticalMap.sectorColor`), not a single-sector-at-a-time view. `hex_delta`/`presence_delta`/`sos_delta`/`report_delta` messages carry their own `sector_id`; the client routes each to that sector's layer group.
- **Report `kind` values are `subject_found`/`medical`/`item_found`/`hazard`/`no_passage`** (the actual `reports.kind` CHECK constraint from migration 0001) -- **not** the shorthand "subject/medical/item/hazard/no-passage" used in this document's own prose elsewhere. Caught by reading the real schema (`\d reports` against the live DB) before wiring up `REPORT_KIND_STYLE` in `map.js`, rather than trusting this document. If you're ever unsure whether a value here is the literal DB/API value or paraphrased description, check the schema.
- **POD-to-color for the hex layer is a straight `hsl(t*120, 70%, 45%)` interpolation** (`map.js`'s `podColor`), red at POD 0 to green at POD 1, clamped -- clamped because a heavily-repeat-covered sector could in principle push `cumulative_pod` past 1.
- **Action buttons (SOS acknowledge/resolve, report acknowledge) don't optimistically update local state.** They fire the REST call and disable themselves while in flight; the actual UI update comes back through the same WS delta path as any other change (the server's own `AFTER INSERT OR UPDATE` trigger fires regardless of who made the change, and the dashboard's own open socket receives its own broadcast same as any other connected client). This keeps one single source of truth for "what the map shows" -- deliberately simpler than maintaining a parallel optimistic-update path, at the cost of a small round-trip delay before a click visibly resolves.
- **Verified manually end-to-end against the real running backend** (docker Postgres + real uvicorn server + the actual browser, via the Claude Browser tool) -- not just "it loads": full login -> create event -> draw+create sector -> live `presence_delta` (device_presence row inserted directly in Postgres, confirmed the marker appeared color-coded within ~1.5s with no page reload) -> live `sos_delta` (SOS marker + tactical panel card appeared, Acknowledge/Resolve buttons both exercised and confirmed the panel/marker updated live) -> live `report_delta` (hazard report marker + panel card appeared, Acknowledge exercised, marker persisted on map per design while the panel entry cleared) -> live `hex_delta` (hex polygon appeared with the correct interpolated color for its POD) -> reconnect-with-backoff (backend process killed and restarted mid-session; the socket reconnected on its own with a fresh ticket, no page reload, confirmed via the connection-status dot). All test fixtures inserted directly into Postgres for this were cleaned up afterward; the event/sector created through the actual UI were left in place as ordinary dev data (consistent with prior sessions' e2e test residue already in the same dev DB).
- **No automated test exists for any of this** -- there's no JS test framework anywhere in this repo (no `package.json`, no test runner), so this phase's verification is manual-only, unlike every other phase's "real infrastructure, real E2E test" standard. If Phase 6c gets extended further, this is the biggest gap worth naming explicitly: either accept manual verification as this component's standard (it's a thin visualization layer over already-tested REST/WS endpoints, which is a reasonable argument) or introduce a real browser test tool (Playwright is the obvious choice) as a new project dependency -- that's a decision worth surfacing to the user, not assuming.

### Follow-up fix: "sector not accepting volunteers" was really "event never started"
- **A user report ("this sector is not currently accepting volunteers" when joining a dashboard-created sector) was diagnosed by the user as a sector-status problem, but it wasn't** -- `sectors.status` defaults to `'open'` in the DB (migration 0001) and `SectorCreate` has no `status` field at all, so there is **no code path, past or present, that could create a sector as anything other than `open`**. The actual gate that was failing: `POST /join` (`routes/memberships.py`'s `join_sector`) rejects if EITHER the sector isn't `open` OR the parent event isn't `active` -- and the dashboard had a "create event" button but nothing to transition it out of `draft` (`events.status` also defaults to a non-accepting state, `'draft'`, per migration 0001). Every dashboard-created event sat in `draft` forever; confirmed empirically against the dev DB (`SELECT id, name, status FROM events` showed every dashboard-created row `draft`, every sector `open`) before writing any fix.

### Follow-up: sector-focused UX (and the Leaflet rAF trap)
- **The shape**: the left sidebar list is deliberately minimal (swatch, name, recruitment status dot, pending-count badge) and is now a *selector*, not a control surface. Selecting a sector -- by clicking its row OR its polygon on the map -- pans/zooms the map to that sector (`TacticalMap.focusSector`, dims the other sectors) and swaps the right panel into a dedicated management view: recruitment toggle, join code, pending approvals, member roster, and SOS/reports filtered to that sector. "← All sectors" returns to the event-wide overview and re-fits the map to every sector.
- **Both right-panel modes render their SOS / pending / report lists into the SAME container ids** (`#sos-list`, `#pending-list`, `#report-list`), so those three renderers exist once and just filter on `selectedSectorId` (`inScope()`). The alternative -- separate renderers per mode -- would have meant four near-duplicate copies of the same card-building code drifting apart. They also drop the "· SectorName" suffix when a sector is focused, since it would be redundant.
- **`GET /sectors/{id}/memberships` is now fetched UNFILTERED** (one request per sector) and partitioned client-side into pending (`status === 'pending'`) and the active roster (`status === 'approved'`), instead of the previous `?status_filter=pending`. One request feeds both the approvals list and the roster.
- **"Make Lead" is COMMANDER-ONLY** (`POST /sectors/{id}/lead` uses `require_commander`, not `require_lead_or_commander` -- a Lead cannot hand off their own role), and the target must already hold an approved membership. The dashboard compares `/auth/me` against `event.commander_id` and renders the button **disabled with a tooltip** rather than hidden, so a Lead can see the capability exists and why it's unavailable. Promotion demotes the previous lead in the same transaction, so two rows change role -- the client refetches rather than patching state locally.
- **"Remove" is `POST /memberships/{id}/revoke`** (approved rows only; 409s otherwise). Its confirm dialog states the real consequence honestly, including the limitation from `memberships_repo.revoke`'s own docstring: the removed device **keeps the sector key** until the epoch is bumped -- what revocation actually does immediately is fail the membership check on the device's next request. Don't reword that into "access removed", it would be a lie.
- **THE BUG WORTH KNOWING (`map.js`): Leaflet's animated `fitBounds` is a silent no-op whenever `requestAnimationFrame` doesn't run.** `Map.setView` delegates to `_tryAnimatedZoom`, which schedules the actual view change inside a `requestAnimationFrame` callback and then returns `true` -- so `setView` believes it succeeded and returns early. In a backgrounded/throttled tab (or a headless, non-compositing browser) that rAF never fires and **the map simply never moves, with no error anywhere**. Worse, `_tryAnimatedZoom` starts with `if (this._animatingZoom) return true;`, and `_animatingZoom` is only cleared by a `transitionend` -- so one missed transition wedges every future `setView` permanently. Symptom seen while building this: focusing a *distant* sector worked but zooming back out did nothing, because a large jump fails `getSize().contains(offset)` and falls through to the synchronous `_resetView` path, while a modest zoom-out takes the rAF path. **Fix: the map is constructed with `zoomAnimation: false`**, which makes every view change a deterministic synchronous snap and removes the wedge risk entirely. If someone re-enables the glide, they are re-introducing "commander clicks a sector and the tactical map doesn't move" for background tabs.
- **Second, unrelated map fix**: `addSector()` no longer calls `_fitAll()` itself. Fitting once per added sector meant N-1 wasted view changes on load, and (with animation on) the first fit's in-flight animation could swallow the later ones. `fitAll()` is now public and the caller invokes it once, after the batch. `fitAll` also builds its union with a fresh `L.latLngBounds([])` rather than mutating the first sector's bounds object.
- **Verified end-to-end in the browser against the real backend**, measuring the map by the rendered pixel bounding boxes of the sector polygons rather than trusting that a click "looked right": fit-all shows both sectors on screen (50x51 and 29x17 px), focusing either enlarges it and pushes the other off-screen (0x0, Leaflet clips), and closing restores the exact fit-all geometry. Then the full management chain with two real volunteer accounts+devices: real `POST /join` x2 -> sidebar badge showed `2` on that sector only -> both approved from the UI -> both appeared in the roster -> Make Lead applied the LEAD badge and removed its own promote button, with `sectors.lead_user_id` and the membership `role` both confirmed changed in Postgres -> Remove revoked the other (confirmed `status='revoked'` in the DB) -> and an SOS seeded in one sector plus a report in the other proved the per-sector filtering (each panel shows only its own; the overview shows both, sector-labelled). Zero console errors throughout.

### Subject record UI + vendored map libraries (dashboard)
- **Context**: these are items 1 and 2 of a top-3 list agreed with the user after an audit that diffed every backend route against what `dashboard/api.js` actually calls. That audit found **five endpoints built and paid for but never wired to any client**: subject GET/PUT, `POST /events/{id}/end`, `PATCH /sectors/{id}/tuning`, and the per-hex contributors drill-down. The subject record was the most glaring — it is the reason the callout exists. The other three remain unwired; see "How to continue".
- **The subject PUT is a full-record UPSERT, not a patch.** `subjects_repo.upsert` does `ON CONFLICT (event_id) DO UPDATE SET` on *every* column from EXCLUDED, so any field omitted from the request body is written as NULL. The edit form is therefore always prefilled from the current record — that is a correctness requirement, not a nicety. Sending a partial body would silently erase the medical notes.
- **`retention_days` is derived on read, not defaulted.** `SubjectOut` returns the absolute `purge_after` deadline but *not* the `retention_days` that produced it. The form recovers it as `purge_after - consent_recorded_at` (valid because the backend sets both from the same `now()` in one statement). This was a real bug caught during verification: the field originally hard-defaulted to 30, so a commander reopening the form to fix a typo would silently extend a real person's PII retention from 14 days to 30. **If `SubjectOut` ever gains a real `retention_days` field, use it and delete the derivation.**
- **PII handling is deliberate, not decorative**: `consent_basis` is client-validated as required (the backend requires it too), the consent timestamp and the auto-purge deadline are shown as first-class rows rather than buried, and medical notes get their own visually-separated red-bordered block because that field is the one most likely to change what a searcher does on contact. Actual purging is Phase 8's job — nothing deletes these rows yet.
- **Commander-only, enforced twice**: the button hides its edit affordances unless `me.id === event.commander_id`, and the backend `require_commander`s both routes anyway. The client check only avoids offering an action that can only 403. A "no subject on file" amber ring on the button nudges the commander, since an event can legitimately be created before the subject's details are known.
- **Vendoring**: `dashboard/vendor/{leaflet,h3-js}/`, pinned to the versions previously loaded from unpkg (Leaflet 1.9.4, h3-js 4.1.0), including Leaflet's `images/` since its CSS references them relatively. **There is no package manager or build step in this project — upgrading means replacing those files by hand**, which is the tradeoff accepted for a no-build dashboard. Verified via `performance.getEntriesByType('resource')` in the live page that no request leaves the origin except OSM tiles.
- **What vendoring does and does not buy**: with no internet the dashboard now still loads and renders sector polygons, coverage hexes, presence/SOS/report markers and every control — only the basemap tiles are missing. Full offline (cached tiles, service worker) was explicitly deprioritised: the command post is typically the one location *with* connectivity (vehicle power, generator, Starlink), whereas the mobile app — already offline-first — is where dead zones actually bite.

### Dev field simulator (`/dev/sim` + `dashboard/sim.html`)
- **What it is**: virtual field units that walk operator-drawn routes and push real telemetry, so multi-user tracking, coverage growth and live dashboard updates can be tested without physical handsets. Reachable at `/dashboard/sim.html`.
- **SECURITY: local-only, guarded twice.** The router mints Ed25519 device identities, self-approves sector memberships and issues session tokens with **no proof of possession** -- a total authentication bypass by design. `main.py` refuses to register it unless `settings.is_local`, AND `dev_sim._require_local` re-checks per request, so deleting either guard alone still fails closed. `test_dev_sim_routes.py::TestLocalGating` asserts both. Startup logs a loud WARNING when it is enabled. **If this ever reaches a deployment, anyone can mint working field credentials with one unauthenticated POST.**
- **Why the crypto lives in Python, not the simulator's JavaScript.** `/ingest` takes XChaCha20-Poly1305-encrypted, Ed25519-signed 27-byte payloads, so a browser simulator would need its own wire-format and crypto implementation -- a THIRD copy alongside Python and Dart, with no interop test holding it to either. Instead the browser asks `POST /dev/sim/units/{id}/encode-points` for opaque base64 blobs (built with the very `wire_format.pack` + `mesh_crypto.encrypt` the pipeline decodes with, so drift is impossible) and then POSTs them to the **real** `/ingest` itself with the unit's **real** session token. Auth, routing and all 11 pipeline stages are genuinely exercised; only the human is skipped.
- **THE BUG WORTH REMEMBERING: `is_mocked` silently produces zero coverage.** The first version flagged every simulated point `is_mocked=True`, reasoning that synthetic positions should be labelled honestly. Result: 22 points **accepted**, and **zero** coverage hexes. `plausibility.usability()` treats a mocked fix as untrustworthy and excludes it from the swath entirely -- "stored for audit but contributes nothing to coverage, full stop" -- which made the simulator structurally incapable of testing the exact thing it exists to test. It also fragmented segmentation (11 points became 11 separate segments instead of 1, because excluded points break continuation). `is_mocked` now defaults to False and is per-point settable; tests assert BOTH directions.
- **`accepted` is not the same as "it worked".** That is the general lesson from the above: a point can be accepted (stored) and still contribute nothing. `hexes_touched` in the ingest response is the signal that coverage actually happened, and the simulator surfaces it as a live stat. Note it is a sum of PER-REQUEST touches, so consecutive points re-touching a cell each count -- 24 points produced "37 hex touches" but **17 distinct** hexes. Query `hex_coverage_state` for the true distinct count.
- **Cleanup is label-scoped, not time-scoped.** Every row the simulator creates is tagged `[SIM]` on the device/user, and `DELETE /dev/sim/units` removes only rows matching that tag, in FK-safe order. A test asserts a genuine non-sim device survives the purge.
- **Unit credentials are in-process only** (`_UNITS` dict), deliberately never persisted: the raw device signing keys and the unwrapped sector key live only in memory, so a backend restart invalidates them rather than leaving usable credentials on disk. The UI must recreate its units after a restart -- the 404 says so explicitly.
- **Sampling mirrors the real app**: a point is emitted every 10m of travel (matching `LocationSamplingPolicy`'s high tier), not on a timer, so a stationary unit produces nothing and segmentation sees the spacing it expects.
- **Verified end to end**, not just unit-tested: 2 units on hand-drawn routes -> 24 points sent, 24 accepted, 0 rejected -> Postgres showed 1 segment per unit (not 11), 8-9 contributions each, 17 distinct covered hexes at POD 0.400 -> the Commander Dashboard rendered exactly those 17 POD-shaded hexes and 2 green presence markers with the WebSocket connected.

### Boundary editing, the tuning recalc, and why they differ
- **THE KEY INSIGHT, and it is counter-intuitive: changing a sector's boundary must NOT recalculate coverage.** The user's initial instruction was to recalc on boundary change; that was investigated before implementing and turned out to rest on a false premise. Two facts, both verifiable in the code: (a) the **ingest pipeline never clips the swath to the sector polygon** — stage 9/10 of `ingest/pipeline.py` buffers the walked track and hexifies it, and there is no `ST_Intersects`/`ST_Within`/`ST_Contains` anywhere in `app/`; (b) **`recalc_hex_coverage()` never reads the boundary** — its only reference to `sectors` is `SELECT repeat_discount`. **Proved empirically** by moving a sector's boundary entirely off a covered hex and re-running the function: POD unchanged, 0.4000 → 0.4000. A recalc call on the boundary path would burn CPU writing back identical numbers while *looking* like a safety measure.
- **This is also the behaviour a callout wants.** `hex_contributions` records where searchers *physically walked*. "We searched this ground" is terrain truth; an administrative outline being redrawn at 2am must not erase it. `test_sector_geometry_and_tuning.py::TestBoundaryEditing::test_redrawing_the_boundary_does_NOT_disturb_coverage` exists specifically to stop a future contributor from "fixing" this by adding a recalc.
- **The recalc that IS needed lives on tuning.** `repeat_discount` is read live by the SQL function, so changing it genuinely re-weights every historical pass — and until this session `PATCH /tuning` changed it with **no recalc at all**, leaving stale `cumulative_pod` values on the map until some future ingest happened to touch each hex. Now `_POD_AFFECTING_TUNING_FIELDS` drives a recalc over `list_hex_ids_for_sector`. Note the set contains **only** `repeat_discount`: `base_pod_day`/`base_pod_night` are snapshotted into `hex_contributions.base_pod` at ingest, so they affect only FUTURE traversals — asserted in both directions by tests.
- **`h3_resolution` is refused, not recalculated, once contributions exist** (409). Existing rows hold cell ids computed at the OLD resolution — the ids themselves would be wrong, not merely their POD, and no recalculation can repair that. Re-sending the *same* resolution is explicitly allowed, so a UI that PATCHes a whole tuning form isn't locked out.
- **`SectorStatusUpdate` became `SectorUpdate`** (status and/or boundary, at least one required via a `model_validator` — an empty body would otherwise 200 having done nothing). The existing status-only tests were unaffected.
- **Geometry helpers are pure and in their own module** (`dashboard/geo.js`): area uses the **spherical excess** formula, not a planar shoelace on raw degrees — at Israel's latitude a degree of longitude is ~15% shorter than one of latitude, so a planar figure would overstate area by roughly that much. Verified against PostGIS's own `ST_Area(geography)`: 42 km² displayed vs 42.33 km² geodesic truth.
- **Self-intersection is blocked client-side** because PostGIS accepts a bowtie ring into a `geography` column without complaint, and H3's `polygon_to_cells` then produces a nonsense cell set for it — surfacing much later as coverage in the wrong place with nothing pointing back at the moment it was drawn. The Finish/Save button is disabled while a ring crosses itself.
- **Vertex dragging is hand-rolled** (`_beginVertexDrag`): Leaflet's `circleMarker` has no drag support and using real `L.Marker`s would mean managing icon anchors for a 6px dot. Map dragging is disabled for the duration so the canvas doesn't pan under the cursor. Midpoint handles insert-and-immediately-drag, which is the only way to ADD detail to an existing outline.
- **End Event's confirmation states real consequences with live counts** (sectors closed, sessions killed) rather than a generic "are you sure?" — it is irreversible and there is no reopen. After it succeeds the sector list is refetched rather than guessed at, since every sector's status became `closed` server-side.
- **Verified end-to-end in the browser against the real backend**, not just unit-tested: seeded genuine coverage on a sector, dragged a vertex through the real UI, saved, and confirmed in Postgres that the geometry moved (42 km² → 50.8 km², min longitude 34.7346 → 34.7192) **while `cumulative_pod` stayed 0.4000 and the contribution row survived**. Drawing UX was exercised by deliberately drawing a bowtie (warning shown, Finish disabled) then undoing back to a valid triangle (warning cleared, Finish enabled). End Event was run on a throwaway event and confirmed `status='ended'` with `ended_at` set.

### Tactical session HUD (mobile): the volunteer's active-session screen
- **What it replaced**: `SessionActiveView` was a centred column of six near-identical outlined buttons, which gave "SOS" the same visual weight as "Sector reports". For a life-safety tool that's the wrong priority ordering, and it's the reason the redesign is a layout change rather than a restyle. It now lives in its own file (`lib/ui/screens/active_session_view.dart`); `membership_status_view.dart` keeps only the small pre-session states (pending/rejected/revoked/claiming).
- **NEW DEPENDENCY: `flutter_map` + `latlong2`** (10 transitive packages). This is the repo's first map library and was previously listed in this document as an open tech-stack decision. Chosen over a hand-rolled `CustomPainter` schematic because `PolygonLayer`/`MarkerLayer`/`CircleLayer` render **without any tiles**, so it is a strict superset: offline you still get the sector outline, your position and your accuracy ring on an empty background; online you additionally get an OSM basemap. A custom painter would have had to reimplement projection and gesture handling to reach the same place.
- **`mapTilesEnabledProvider` exists specifically so widget tests can switch the basemap off.** `TileLayer` issues real HTTP per tile and leaves image-load timers pending, which trips the test binding's no-pending-timers assertion (gotcha #10's family). Turning it off in tests is not a fudge: it renders the exact same vector layers a searcher sees in a dead zone, so the tested path IS the offline field path.
- **The HUD reads position and battery from `TrackingActive`, it does NOT open its own GPS stream.** `TrackingActive` gained two optional fields (`lastSample`, `batteryPct`) which the controller already had in hand at both construction sites. A second `LocationSource` subscription purely to draw a map dot would have quietly undermined `LocationSamplingPolicy`'s whole battery-tiering scheme -- battery is a first-class constraint in this app, not a detail. Both fields are optional so the ~dozen existing tests that construct `TrackingActive` still compile unchanged.
- **Hold-to-activate, not tap-then-confirm.** `HoldToActivateSosButton` requires a continuous 1.5s press (`sosHoldDuration`) with a filling progress ring; releasing early rewinds silently. This deliberately differs from `SosButtonView`'s confirmation DIALOG, which is still used on that screen: a dialog needs a second accurate tap on a small target, which is the harder action in exactly the conditions where SOS matters (cold, gloved, one-handed, panicking). Releasing early is silent on purpose -- an "SOS cancelled" toast every time a phone shifts in a pocket trains searchers to ignore the UI.
- **Quick-report grid is two steps, not one.** A tile picks the kind and opens `ReportFormView` (which gained an `initialKind`) rather than filing immediately, because a report's location is captured from a fresh GPS fix at SUBMIT time -- one-tap filing would attach a position the searcher never saw. `reportKindPresentation` is keyed by the exact wire-format `reportKinds` values, not display shorthand (see gotcha #17 for why that distinction keeps biting).
- **`GeoPoint.fromGeoJson` is the single place the coordinate order is swapped.** GeoJSON is `[lng, lat]`; every map widget and the rest of this app is `(lat, lng)`. A flipped pair doesn't throw, it just silently puts the sector in the wrong hemisphere, so the swap happens once, in one constructor, and a test asserts it with deliberately asymmetric fixture values (~31.7 lat vs ~35.2 lng) so a regression is visible rather than plausible.
- **`activeSectorProvider` returns null instead of throwing** when the boundary can't be fetched -- a searcher in a dead zone still needs SOS, reports and their own position, so the map degrades to "position only" with an on-map notice rather than the screen erroring out.
- **A real layout bug was caught by the new tests, not by eye**: the quick-report sheet overflowed its default `showModalBottomSheet` height cap (9/16 of screen) by 213px, pushing the second grid row -- hazard and no_passage -- off-screen and untappable. It would have shipped as "two of the five report types don't work" on short screens and in landscape (a phone in a chest mount is an ordinary SAR setup). Fixed with `isScrollControlled: true` + a `SingleChildScrollView`.
- **NOT verified on a device.** The Android toolchain is still incomplete (gotcha #2), so this screen has never actually been rendered on hardware or an emulator -- only through widget tests and `flutter analyze`. Map gestures, tile loading over a real cellular link, and the hold gesture with a real finger are all unverified. That gap is the single biggest caveat on this work.

### Testing philosophy established across every phase
**Prefer real infrastructure over mocks, and only mock at the outermost I/O boundary.** Concretely:
- Real Postgres (Docker) for all DB-dependent backend tests — never a mocked database.
- Real libsodium for all crypto tests — never a fake crypto implementation.
- Real running backend server for the mobile e2e test — only the HTTP transport layer is ever mocked (via `http`'s `MockClient`), never the business logic.
- DB-dependent tests skip gracefully (not fail) when the database is unreachable, via a `db_conn` fixture pattern — but tests needing a **real commit** (anything depending on `NOTIFY` delivery, which only fires post-commit) use an independent, non-rollback connection instead of the standard rollback-wrapped fixture.

## 4. Known gaps and gotchas (read before debugging blind)

1. **Flutter web target doesn't work yet.** The `sodium` package needs a manual JS-libsodium-asset download step for web builds (its own README calls this out) that was never done. Not a bug, just unfinished — orthogonal to everything else. `web/` and `windows/` platform folders exist in the repo (added during this session's debugging) but web specifically will hang on a blank splash screen forever if you try to run it without that extra step.
2. **~~Android toolchain is incomplete.~~ RESOLVED 2026-08-05** -- `flutter doctor` is now fully green (Android SDK 36.0.0, all licenses accepted, Visual Studio Community 2022 present, physical device detected). Android APKs build successfully. See gotcha #25 for the one Windows-specific build trap that remains, and #26 for the MIUI install block.
3. **Server output buffering**: if you ever redirect the backend's stdout to a file or pipe it through a task runner / IDE console, Python block-buffers non-TTY output and log lines can sit unwritten for a long time. Always run with `python -u` (or `PYTHONUNBUFFERED=1`) when output isn't going straight to a visible terminal.
4. **`10.0.2.2` is Android-emulator-only.** If you ever see a Flutter client hang on any network call with nothing reaching the backend, check `mobile/lib/core/platform_base_url.dart` and confirm the target platform is being detected correctly — this exact bug already happened once this session.
5. **Don't trust an analyzer-suggested rewrite without checking its actual behavior.** `flutter analyze`'s own suggestion to rewrite `if (label != null) 'label': label` as `?'label': label` silently changed the semantics (null-checks the map *key*, not the *value* — the key is a string literal, so the entry was always included). Caught by direct empirical testing, not by reading documentation. If `flutter analyze` suggests a rewrite involving `?` on a literal map key, verify it doesn't change behavior before applying it.
6. **Battery percentage in the join-code UI is still user-entered** (a slider) — Phase 5c added `BatteryPlusInfoProvider` for real device battery, but only for the location-tracking sampling policy, not (yet) wired back into the join-code UI's slider. Leave as-is unless asked to change it; it's a deliberate scope boundary, not an oversight.
7. **`MembershipInfo.role`/`movementMode` from the backend must be threaded through the join flow explicitly** — an earlier draft of `JoinController` hardcoded placeholder values instead of using the real fields already returned by `GET /memberships/{id}`; this was caught and fixed, but if you're extending the join flow, make sure new state transitions keep passing these through rather than reintroducing placeholders.
8. **`sqflite_common_ffi`'s isolate-backed `databaseFactoryFfi` does not work inside `testWidgets`** (Flutter's widget-test zone) — its background isolate's replies arrive via the real event loop in a way `tester.pump()` never observes, so any `await` on it can hang indefinitely while pumps keep getting issued. Use `databaseFactoryFfiNoIsolate` (same package) for any widget test that touches `TelemetryBufferStore`; the plain, non-widget `test()`-based controller test uses the normal isolate-backed `databaseFactoryFfi` instead, since a bare `test()` isn't wrapped in that zone. See `mobile/test/ui/screens/location_status_view_test.dart`'s `setUp` for the concrete pattern.
9. **`TelemetryBufferStore` opens with `singleInstance: false`.** `sqflite_common`'s factories cache open connections by literal path string when `singleInstance` isn't set to false — every test using the literal `inMemoryDatabasePath` (`':memory:'`) would otherwise silently share ONE underlying connection across different `TelemetryBufferStore` instances, and close()/open() timing races between tests caused real (previously debugged) cross-test data leakage. If you ever see a `TelemetryBufferStore`-related test with an inexplicably wrong row count, check this first.
10. **A real `Timer`-owning controller (like `IngestSyncController`) must be stopped as the LAST STATEMENT inside the `testWidgets` body itself, not via `tearDown` or `addTearDown`.** Flutter's test binding asserts no `Timer` is still pending as part of `_runTestBody`, which runs BEFORE both `tearDown` and `addTearDown` callbacks get a chance to fire — so `container.dispose()` (which would otherwise cancel the timer through the controller's own `dispose()`) is always too late if only called from `tearDown`. See `location_status_view_test.dart`'s `stopControllers()` helper and its usage for the working pattern.
11. **A bare `await Future.delayed(...)` with no `tester.pump()` calls around it can hang indefinitely inside `testWidgets`** — real Timer/event-loop progress in that test binding only reliably happens interleaved with `pump()` calls. Any "wait for something timer-driven to happen" in a widget test must go through a `pump()` loop (see `pumpUntilFound` in `location_status_view_test.dart`), never a standalone delay. This is a DIFFERENT issue from gotcha #10 (or from Phase 5c's `sqflite_common_ffi`-under-FakeAsync gotcha) but produces the same symptom (a hang), so if a widget test hangs, check for a bare `Future.delayed` first — it's the cheapest thing to rule out.
12. **After adding a new route to `main.py`, the ALREADY-RUNNING backend server process is still serving the OLD code until restarted.** Hit this directly this session: `POST /sos` 404'd against the running server for several minutes of debugging before realizing the fix was in the code, not the test -- the uvicorn process just hadn't picked up the new router registration (it wasn't started with `--reload`). If a route you just added/changed 404s or behaves like it doesn't exist, restart the server (`netstat -ano | grep :8000` to find the PID, kill it, relaunch per Section 1's start command) before debugging further.
13. **There is still no WebSocket client anywhere in the Flutter app.** The backend's realtime broadcast (coverage/presence/SOS deltas, all three now) is fully built and proven end-to-end from the SERVER side (`test_ws_dashboard.py`, `test_sos_routes.py::TestRealtimeBroadcast`), but nothing on the mobile side subscribes to it -- `SosAlertsView`'s Lead/Commander list uses plain REST polling (`Timer.periodic`, 5s), same convention as `PendingApprovalView`. Building a real WS client in Flutter (ticket fetch -> connect -> handle `hex_delta`/`presence_delta`/`sos_delta`) is still open work, likely warranted once there's a concrete reason to want push latency instead of a 5s poll.
14. **Postgres's `now()` is frozen at TRANSACTION START, not per-statement** — `conftest.py`'s `db_conn` fixture wraps a whole test in ONE transaction, so two sequential inserts under `db_conn` can get the IDENTICAL `now()`-derived timestamp, breaking any assertion that depends on strict ordering or a `updated_at > checkpoint` delta query. Hit this writing `test_sos_repo.py`'s `TestListAndDeltaQueries` (two triggers landed on the same `triggered_at`, and a resolve's `updated_at` didn't compare greater than its own trigger's checkpoint). Fix: use a local `real_conn` fixture (separate `asyncpg.connect()`, no wrapping transaction, manual cleanup -- same shape as `test_ws_dashboard.py`'s) for any test that needs `now()` to actually advance between statements; `db_conn` is still correct and preferred for everything else (its transaction-per-test isolation is exactly what most tests want).
15. **ALWAYS check whether a table already exists (especially anything named in Phase 0's schema) before writing a migration that assumes a fresh one.** This bit hard this session: `reports` looked like a natural Phase 6b table to create from scratch, but it already existed from `migrations/0001_init.sql` with a far more sophisticated design (Ed25519 signature dedup, `delivery_path`/`hop_count` for mesh, matching `track_points`) than a first, wrong assumption of plain CRUD. A migration that tried `CREATE TABLE reports` again failed loudly (`relation already exists`) -- but a few of ITS OTHER statements (the NOTIFY trigger/function, which don't check for table existence) silently succeeded against the pre-existing table before the mistake was caught, and had to be manually reverted (`DROP TRIGGER`/`DROP FUNCTION`) before writing the correct migration. If any future phase needs a table, grep all of `migrations/*.sql` for its name FIRST -- don't assume Phase 0's schema is empty just because nothing built on it yet.
16. **`docker exec <container> psql ...` needs `-i` to accept piped/heredoc stdin.** Without it, `docker exec lifesearch-db psql -U lifesearch -d lifesearch <<'SQL' ... SQL` runs, exits cleanly with no error and no output, and silently does NOTHING -- psql just sees a closed/empty stdin instead of the heredoc content. Cost real time this session (inserted rows for manual WS-delta testing appeared to succeed, then a `SELECT` proved the table was unchanged). Always `docker exec -i` when piping SQL in.
17. **Report `kind` values in the actual schema/API are `subject_found`/`medical`/`item_found`/`hazard`/`no_passage`**, not the "subject/medical/item/hazard/no-passage" shorthand used elsewhere in this document's own prose (including its own Phase 6b section above). Caught by checking `\d reports`'s CHECK constraint directly against the live DB rather than trusting this document while wiring up the dashboard's per-kind marker styling. A reminder that this file can itself be a source of a subtly-wrong assumption -- verify against the schema/code when a value actually matters, the same standard applied to trusting this document's claims about test counts or server state.
18. **A volunteer join needs BOTH the sector `open` AND the event `active` -- checking only one gate when debugging a "can't join" report will send you looking in the wrong place.** `routes/memberships.py`'s `join_sector` checks `sector.status != "open" OR event_status != "active"` and returns the exact same opaque error ("this sector is not currently accepting volunteers") for either cause -- by design, same "one opaque error for every rejection reason" pattern as the OTP flow, but it means the error message itself gives zero hint about which of the two gates actually failed. A user this session reported the error and (reasonably) assumed it was about sector status; the real cause was the EVENT never having been started (`events.status` defaults to `'draft'`, and nothing called `POST /events/{id}/start`). If this comes up again: `SELECT status FROM events WHERE id = ...` and `SELECT status FROM sectors WHERE id = ...` both, don't assume which one is wrong.
19. **Leaflet's animated `fitBounds`/`setView` silently does nothing when `requestAnimationFrame` isn't running** (backgrounded tab, throttled tab, headless/non-compositing browser) -- `_tryAnimatedZoom` schedules the real view change in a rAF callback and returns `true`, so `setView` returns early believing it worked. No error, no movement. It can also wedge permanently: that method early-returns forever if `_animatingZoom` is left `true` by a `transitionend` that never arrives. `dashboard/map.js` therefore constructs the map with **`zoomAnimation: false`** -- do not "restore the nice glide" without understanding you are trading it for silent, unreproducible map failures. Confusing detail while diagnosing: LARGE viewport jumps still work, because they fail Leaflet's `getSize().contains(offset)` check and fall through to the synchronous `_resetView` path -- so "focusing a far-away sector works but zooming back out doesn't" is the signature of this bug, not two separate ones.
20. **Verify map behaviour by measuring the rendered polygon geometry, not by eyeballing a screenshot** (and note screenshots don't work at all when the Browser pane isn't displayed). `document.querySelectorAll('.leaflet-overlay-pane svg path')` + `getBBox()` gives each sector's on-screen pixel box; Leaflet clips off-screen paths to `0x0`, so "which sectors are visible and how big" is directly assertable. That is how gotcha #19 was caught -- a screenshot would have looked plausible, and `fitBounds` returning normally proved nothing. Patching `L.Map.prototype.fitBounds` from the console to log its arguments is also a fast way to separate "we passed the wrong bounds" from "Leaflet ignored us".
21. **A press-and-hold test needs a bare `pump()` between `startGesture()` and the pump that advances the clock.** `onTapDown` doesn't fire on the pointer-down event itself -- it fires when the gesture arena resolves, which happens during the NEXT pump. So `startGesture(); pump(holdDuration)` starts the hold only at the very END of that frame, the timer never advances, and the hold never completes. The dangerous half is the inverse: a "short press must NOT trigger" test **passes for the wrong reason** under the same mistake, because the press never registered at all. Both directions have to be asserted, with a `pump()` first, or the test is decorative. See `test/ui/screens/active_session_view_test.dart`.
22. **A widget's layout only gets checked when a test actually renders it at a real size.** The quick-report bottom sheet overflowed `showModalBottomSheet`'s default 9/16-of-screen cap by 213px, silently pushing two of the five report tiles off-screen and out of reach -- `flutter analyze` is completely blind to this, and it would have shipped as "hazard and no_passage can't be tapped" on short screens and in landscape. Overflow shows up as a `RenderFlex overflowed` exception in the test output, so any new sheet/dialog/grid is worth one widget test purely to force a layout pass. Fix pattern: `isScrollControlled: true` plus a `SingleChildScrollView`.
23. **Coverage is NOT clipped to the sector boundary, and that surprises almost everyone.** `hex_contributions` records where searchers physically walked (ingest buffers the track and hexifies it -- no polygon intersection anywhere in `app/`), and `recalc_hex_coverage()` reads only that ledger plus `repeat_discount`. Consequences worth internalising before touching either: (a) redrawing a boundary changes no POD, so a recalc there is pure theatre -- there is a test asserting this; (b) hexes can legitimately sit OUTSIDE their sector's outline, which is correct, not corruption; (c) any future "% of sector searched" metric cannot just sum `hex_coverage_state` -- it would have to intersect against the boundary itself, which nothing currently does.
24. **Of the tuning fields, only `repeat_discount` retroactively changes coverage.** `base_pod_day`/`base_pod_night` are snapshotted into `hex_contributions.base_pod` at ingest time and read back from there by the recalc, so changing them affects FUTURE traversals only. `h3_resolution` is in a third category entirely: it can't be recalculated at all (the stored cell ids, not just their POD, would be wrong), so it is refused with a 409 once any contribution exists. If a tuning field is ever added, decide explicitly which of these three buckets it falls into -- `_POD_AFFECTING_TUNING_FIELDS` in `routes/sectors.py` is the switch.
25. **Cross-compiling libsodium for Android on Windows needs a WORKING `make`, and Git for Windows' `make.exe` may be silently broken.** `sodium`'s build hook uses Autotools for the Android/Linux targets; the Windows target uses MSVC + `VsDevCmd.bat` and never touches `make`, which is exactly why `flutter build windows` succeeds while `flutter build apk` fails. The hook locates bash via `where bash`, which lands on Git for Windows, so it also picks up Git's `make`. On this machine that binary is broken -- `make.exe --version` exits 127 with `error while loading shared libraries: ?: cannot open shared object file`, and a Git update did not repair it. The failure surfaces deep in `config.log` as `config.status: error: Something went wrong bootstrapping makefile fragments`; the `ld.lld: error: undefined symbol: memset_s` lines just above it are NORMAL configure feature probes, not the cause -- do not chase them. **Fix, without touching any package:** put the NDK's own GNU Make 4.3 (native Windows, no MSYS dependency) ahead of Git's on PATH:
    `export PATH="$LOCALAPPDATA/Android/sdk/ndk/<version>/prebuilt/windows-x86_64/bin:$PATH"`
    Verified end to end: produces a correct `ELF 64-bit LSB shared object, ARM aarch64` libsodium.so, bundled into the APK as `lib/arm64-v8a/libsodium.so` (315KB stripped).
    **Do NOT "fix" this by switching to `sodium_libs`.** That package is DISCONTINUED (pub.dev `replacedBy: sodium`) and itself depends on `sodium: ^4.0.3`, so it adds a dead wrapper over the very same build hook. `sodium` 4.x also has no "use prebuilt binaries" option: the hook always builds from its bundled tarball, and native assets register the library through the hook rather than by name, so dropping a `.so` into `jniLibs` is not picked up either. The only supported bypass, `NIX_SKIP_SODIUM_BUILD_HOOKS=1`, leaves the package non-functional by the hook's own admission -- useless here, since the app resolves `sodiumProvider` at startup.
27. **`/dev/sim` is an authentication bypass that must never leave local.** It mints device identities and sector sessions with no proof of possession. Two independent guards (registration in `main.py`, plus `_require_local` per request) and a test class enforce this. If you add an endpoint there, re-read `dev_sim.py`'s module docstring first.
28. **A point being `accepted` by `/ingest` does NOT mean it contributed to coverage.** `plausibility.usability()` silently excludes any fix flagged `is_mocked` or below the sector's `min_accuracy_m` -- it is stored for audit and contributes nothing, with no error anywhere. Check `hexes_touched` in the response (or query `hex_coverage_state`) before concluding ingest "worked". This cost real debugging time when the simulator defaulted `is_mocked` to True and produced 22 accepted points with zero coverage; the same trap applies to any real device with poor GPS accuracy.
26. **MIUI/Xiaomi blocks `adb install` by default.** `INSTALL_FAILED_USER_RESTRICTED: Install canceled by user` is not a code, ABI or signing problem -- MIUI requires *Developer options -> Install via USB* to be enabled (which typically also needs a signed-in Mi account with connectivity before the toggle will stick). Nothing on the host side can work around it; it is a physical setting on the handset.
